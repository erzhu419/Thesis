**公交 MC-WM v2：局部区间与模型 TD 诊断**

这是开发诊断批。旧冻结实验、`mcwm_closed_loop_v1` 和 `mcwm_closed_loop_formal_20261020` 均只读；新代码、日志与结果只写本目录。服务器直接读取已驻留的旧输入，不复制或下载 checkpoint。

控制臂为 `real1`（1×真实 TD）、`real075`（0.75×真实 TD）、`model`（旧 A2）、`context`（旧 A3）。全部沿用五个种子、24,000 秒、9,000 秒同一路段限速、285 条目标记录和 456 次策略更新。`model−real075` 隔离模型贡献，`real075−real1` 检查真实 TD 缩放，`context−model` 检查原全局 context。每包第一次更新观察实际 minibatch 的 TD 梯度、绝对 trust 和参数变化，不增加优化步骤或随机抽样。

独立共同预测流比较三种局部预测器：冻结 source 同车区间先验、在线线性参数适应、同一在线模型加每线路残差校准。先用一次固定策略 source 日取得真实同车同 trip 的相邻站标签；仅用受影响三线路的指定区间，不能用全网控制转移冒充同车标签。预测对象包含执行 holding、行驶/信号和下一站服务。目标标签延迟 30 秒，先评分后学习，跨越冲击的区间单列；仅 `available_at<=18000` 的标签用于学习。这是单独计数的物理诊断数据，不进入控制或原全局世界模型，新的局部校准也不等同于旧 A3。

服务器保留必要 JSONL，最终只拉 `diagnostic_summary.json`，其中包含完整性、种子配对效果、局部预测与模型 TD 摘要。不会下载原始轨迹、CSV 或模型。预检和开发结果不能当作下一批正式确认。

执行顺序：`python launch.py stage` → `source` → 源校准完整后 `preflight` → 原生预检通过后 `submit` → `finalize` → 完成后 `collect`。每次提交都会保存任务清单，已有输出不覆盖。

本版先回答局部预测是否适应、模型贡献是否被信任权重压低或与真实梯度冲突、更新是否改变执行动作；再结合稳定/限速两场景的绝对乘客成本决定下一批正式协议。
