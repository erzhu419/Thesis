# v27：整包更新的局部归因

比较同一个 fresh 主日轨迹、同一状态及优化器/RNG 快照下，连续 8 步使用 fresh 结果与完整历史替换的影响。这回答当前前缀上的局部更新效应；两臂共享此前已经学习到的 fresh 信息。

- 固定 seed 6201/6202 × 稳定/冲击四日。每个主日保留 285 个反馈槽、456 次更新、24000 秒目标时长及原初始化。
- 采样器、特征、统一执行规则 F、物理基线和 trust 均沿用原实现。no_fresh 影子用 64 条完整历史结果替换从截至该锚点全部已入库 recent 反馈中采样的 64 条 fresh 结果，actor/value/温度仍使用共同的新状态与动作。
- 固定更新截止点 9000、9300、11700、18000 秒；9000 包含冲击前已完成的标签，不能解释为冲击后监督。
- 每个锚点比较包内 5 条反馈，以及固定窗口内三条线路各自的首个真实状态。后者仅用于评估，不参与训练或实际动作选择；18000 锚点使用 18300–18600 秒真实状态，不改写时钟。
- 分解 reward、bootstrap、Bellman 目标、critic、actor 提案及统一 F 后的 holding；包内反馈与状态探针分别汇总，缺失、零时长及 terminal 单列。

额外诊断开销单列：四个主日回放合计 96000 秒原生仿真、1140 个主日反馈槽与 1824 次主日更新；影子额外 256 次优化器更新，新增目标标签和真实控制分支均为 0。

首个 seed 6202 冲击日运行到 9000 锚点后，必须确认影子未改变主学习状态/RNG、fresh 影子与实际后续 8 步精确一致，以及主日前缀与旧结果一致。该进程继续跑完整日，不重复短预检；通过后其余三日以 high 优先级并行提交。

整日还须精确复现旧 trace、57 个更新记录、反馈 receipt、成本和指标，并确认停更后零训练。汇总只在服务器端读取这些文件，本地只收不超过 60 KB 的小型 JSON。

运行：`launch.py stage` 后启动 `continue_batch.py`。本地协调进程依次完成预检、其余三日和服务器端汇总，不自动提交真实控制分支。后续是否增加少量分支，取决于目标分解、动作价值变化与 F 后 holding 是否呈现可验证的具体差异。

本地验证：影子状态/RNG 恢复、fresh 主更新复现及汇总计算共 8 项测试通过。原生精确复现由服务器预检与完整日结果判定，测试通过本身不代表 fresh 带来控制收益。
